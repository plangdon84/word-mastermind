# CLAUDE.md

## Mission

This repo's mission is to **build and deploy a web app for Word Mastermind**, a
2-player word-guessing game. The full rules live in `README.md` — treat that as
the source of truth and keep it updated when rules change.

## Current phase

Phase C, 1.0 readiness: every mode is built, reviewed and tested (items
13c to 17), and item 18 launches it. The core game logic lives in `src/game/`
(a pure TypeScript module with no UI imports), with Vitest tests next to it.
Run `npm test` and `npm run typecheck` before committing.

- Word validation currently checks the length (5 characters, after trimming
  and lowercasing), that it contains only the letters a–z, and, for secret
  words only, that no letter repeats, then that the word is on the secret or
  guess list (`isValidSecretWord` / `isValidGuessWord` in `src/game/words.ts`).
- The word lists are generated by `wordlist/etl.py` (Python, standard library
  only) from ESDB at a pinned commit; see `wordlist/README.md`. Edit the rule
  files in `wordlist/rules/` or `wordlist/config.json`, then run
  `npm run wordlist` and `npm run test:wordlist`. Never hand-edit
  `wordlist/lists/`. `src/game/wordLists.ts` imports `secret.txt` and
  `guess.txt` as text (Vite `?raw`, typed in `src/raw.d.ts`), so the lists
  ship in the bundle and are never fetched at runtime.
- The same ETL run writes `wordlist/lists/definitions.json` from Open English
  WordNet (pinned by URL and SHA-256; `wordlist/definitions.py`). Fix a bad or
  missing definition in `wordlist/rules/definitions.txt`, never in the JSON.
- The UI is Preact in `src/app/` (Vite; `npm run dev`, `npm run build` →
  `dist/`). Single player, two player vs. computer, a friend or a random opponent, Solo Rush, Daily Rush, the Daily Word, Rush with Friends and Competitive Rush are playable at Easy,
  Medium, Hard and Extreme (Easy everywhere but rated play; README "Easy"). Keep game
  rules in `src/game/` and only presentation in `src/app/`. Nothing may load
  from a third-party host at runtime (fonts are bundled via fontsource).

  derived state. Game logic never reads the clock or `Date.now()`: time is an

## Rules summary (see README.md for detail)

- Each player picks a secret word: a single English word, exactly 5 letters,
  letters A–Z only, not a proper noun, **no repeated letters**. It never changes during the game.
- Players alternate guesses. A guess: a single English word, exactly 5 letters,
  letters A–Z only, not a proper noun; **repeated letters are allowed**.
- Evaluating a guess against the opponent's secret word:
  1. If guess == secret word → guesser wins.
  2. Otherwise response = `|set(guess) ∩ set(secret)|` (count of distinct shared
     letters; position ignored). Only the number is revealed, never the letters.
- Example: secret `beach`, guess `bunny` → 1 (shared `b`).
- An anagram of the secret word scores 5 but is not a win.
- Players track guesses and deduced in/out letters; first to guess the
  opponent's word wins.

## Decisions so far (see README.md for detail)

- The app computes scores automatically. Words and guesses are case-insensitive.
- Validity means "on our own word list": a secret list (no repeated letters,
  common words) and a broader guess list (a superset of the secret list).
- Turn order is random. There is no guess limit. In two-player mode, if the
  player who went first finds the word, the other gets one final guess; a hit
  is a draw. If the second player finds it first, they win outright.
- The app opens on a title screen (single player or two player; opponent,
  computer strength, your difficulty). Two player vs. computer: game logic in
  `src/game/twoPlayer.ts`, the computer's guesser in `src/game/computer.ts`
  (strengths Casual / Skilled / Expert / Mastermind recall 9.5 / 19 / 38 / 100%
  of past scores, and always a score of 5, averaging ~28 / 18 / 12 / 7 guesses), UI in
  `src/app/TwoPlayerScreen.tsx` (see README "Two player vs. computer"). If the
  word lists change, `computer.test.ts` checks the strengths still hit their
  targets.
- Easy (Dev Plan item 13c, README "Easy"): `deduceMarks` (`src/game/deduce.ts`,
  sharing `forEachFittingSet` with `marksFitScores`) marks letters from the
  scores alone; screens show them with `useShownMarks` (`src/app/easyMarks.ts`).
  `isRatedDifficulty` keeps Easy out of rated play (`easy-unrated`). Suggest
  (`src/game/suggest.ts`, `FEATURES.suggest`) offers a secret-list word
  that fits every score; it's a recorded `suggest` move in every engine,
  once a game (a word in a Rush), with worker routes for
  friend games, Daily Rush and lobbies; the app picks the word
  (`src/app/suggestion.ts`).
- Difficulty levels: Easy (the app deduces in/out letters from guess-history
  letter logic only, never the word list), Medium (manual in/out marking that
  highlights across all guesses), Hard (a list of guesses and their numbers
  only), Extreme (no guessed words shown except the latest, which stays with
  its score until the next guess; a scores-only history is shown, subject to
  calibration).
- UI (see README "User Interface"): round letter bubbles; history lines read
  `guess – score`, newest at the bottom. Marks: unmarked = white on black,
  in = white on green, out = black on grey. Medium: tap cycles
  unmarked → in → out → unmarked, applied to that letter in every guess.
  Hard: all unmarked, no interactivity. ☰ Highlights: Check for mistakes (do the
  marks fit the scores? letter logic only, `marksFitScores`) and Clear all highlights.
  Header rows: name/profile/☰ (New game is in ☰); You vs. opponent and difficulty; your
  marked-in letters (your tab) or your word (computer's tab); then the tabs.
  This game's difficulty, How to play, Give up and Exit to main menu live in
  the ☰ menu; guess order (per difficulty) and default difficulty are profile settings. Two player offers your last 10 secret words
  (`src/app/recentSecrets.ts`).
  An ⓘ button before each guessed word shows its definition; definitions are bundled from Open
  English WordNet at build time (no runtime network dependency).
- Modes: (1) single player, (2) two player vs. computer, (3) PvP against a
  friend (by link, or a challenge from the friends list), live on a chess
  clock (15 / 10 / 5 minutes each) or correspondence (1 or 3 days per guess,
  then concedes), and (4) Solo Rush, Daily Rush and Rush with Friends are
  built, as is (3) PvP against a random opponent (the matchmaking queue);
  (4) Rush is a choice of kind (README "Rush modes"), each 4 words.
  Solo Rush: 4 random words against a stopwatch that pauses while you're
  away (no backend; engine in `src/game/run.ts`, UI in
  `src/app/RushScreen.tsx`); its result ranks your score by the computer
  strengths (`strengthForAverage`: < 10 Mastermind, < 15 Expert, ≤ 20
  Skilled, else Casual). Daily Rush: the day's themed set
  (`wordlist/themes/`, never shipped in the app; the day flips at midnight
  in New York, `src/game/dailyDays.ts`), once a day, difficulty chosen
  once, Pause recorded as moves (item 18y), giving up leaves no entry, a leaderboard per day and difficulty by total guesses (time breaks
  ties) with position and percentile. Rush with Friends: a lobby of up to 5
  (join code; computers can fill seats, pacing their guesses by duration ÷
  4 ÷ their strength's fewest expected guesses), one difficulty, the same
  4 server words, a shared clock that never pauses. Competitive Rush: the
  same, but each player sets a word and solves the other 4; rated. They
  share one multi-word run engine.
- Scoring (README "Scoring"): record raw guesses and seconds per word. Score =
  average guesses per word × difficulty factor (Medium 1.0, Hard 0.9, Extreme
  0.8, to be tuned; `src/game/difficulty.ts`), lower first, time breaks ties;
  composite (seconds × guesses) was rejected. A run is scored at the easiest
  difficulty used (difficulty changes are recorded moves). In PvP, difficulty
  never affects the outcome; it's fixed in a rated game and the queue pairs
  players at the same difficulty (whether it should count is open).
  A word given up or unsolved scores max(guesses used, worst solved count for
  that word in the group) + 10, and max(seconds used, worst solved time for
  that word); if nobody solved it, use the group's worst solved result.
  Solo Rush has no group, so a word given up uses your own worst solved word
  in that Rush; giving up a word always warns first that it hurts the score.
- Profile overhaul (Dev Plan item 13, README "Profile" Layout): the profile
  is a hub of section rows (`src/app/profilePages.ts`), each a subpage;
  `onProfile(page)` opens one (the badge toast opens `achievements`). Friend
  games, Daily Rush and lobbies join the history as server modes
  (`SERVER_MODES` in `src/game/history.ts`): the worker builds each
  player's entries from its `games` table (`worker/src/played.ts`,
  `GET /api/played`; entry IDs are hashes, since a game's ID is a
  credential), the app saves them (`src/app/playedGames.ts`), and sync
  never uploads them. Reviews reuse `FriendScreen` and `RushScreen` with a
  `review` (`src/app/reviews.tsx`).
- Unlocking modes (Dev Plan item 13, README "Unlocking modes"):
  `src/game/unlocks.ts` (`computeUnlocks`, `openModes`), pure over the
  saved games like achievements, each step needing the one before; the
  title screen locks what isn't open (`open` prop), and each step has a
  badge (`unlock-*`). Achievements also has Daily Rush badges (each
  difficulty, a streak of Daily Rush days), friend, lobby and Competitive Rush wins,
  and Achievement Hunter (`hunter-*`, 25–100% of the other badges, Easy's
  included). Item 13d's rules (README "Achievements"): a solve is any word
  you found in any mode (two player too, a win or a draw); VS CPU badges
  are per strength and difficulty (`cpuBadgeId`); Suggest voids only the
  few-guesses badges; every Rush earns a level from your own run
  (`scoreSoloRun`, where a lobby's time-out isn't ending early).
- Shared Rush words (Dev Plan item 13): each player gets them in their own
  order, picked by the server (`shuffled` in `src/game/run.ts`; Daily
  Rush's `DailyDeps.random`, a lobby seat's `order`), and the group
  penalty compares words by `seatKeys`.
- Stay lean: a static site first, and a backend only when PvP needs one.

  Later: Workers + Durable Objects + D1 (no Supabase).

## Dev plan

`docs/dev-plan.md` is the build order: one numbered item per PR, one bullet
per commit. When asked for "the next PR in the dev plan", take the first
unchecked item (the first under **To build**), follow its commit breakdown,
tick its box in the same PR and move it to the top of **Done** (latest first).
If the plan changes, update `docs/dev-plan.md` first. Item numbers never shift: a new item
takes a letter (like 13b).

When the owner says "start the next dev item" (or names one), it always
means this repository's (`plangdon84/word-mastermind`) `docs/dev-plan.md`,
read after a fresh pull of `main` (`git fetch origin main` and
`git pull origin main`, or a new branch from `origin/main`), never a stale
checkout or another repo's plan.

**The owner checks the release note before any commit.** Before the first
commit of a dev item (and before any later commit that adds or changes a
release note in `src/app/releases.ts`), show the owner the proposed
version and its one-line notes, or say the PR adds none and why, and wait
for their OK. This comes ahead of "open a draft PR after its first
commit" below.

## Working rules

Agreed with the product owner in the retrospective of 29 September, and
the review and CI rules in the review of 2 October (PRs #63 to #89).

- **Open a draft PR at the start** of a Dev Plan item, after its first
  commit, and push to it as work lands, so the preview URL exists early.
  Don't ask before opening it. Mark it ready only when `npm test` and
  `npm run typecheck` pass and, under the review gate, its review is done:
  marking it ready starts the browser tests and Lighthouse (about 15
  minutes), which drafts skip. Run the browser tests for the screens you
  touched in the session first (`npx playwright test e2e/<file>`), in
  Chromium and WebKit, so the ready run passes the first time and `main`
  (which adds WebKit) stays green.
- **Keep PRs small:** one feature, or at most about five issues, per PR.
  Split a bigger item into several PRs, each with its own bullet.
- **Issues live in the private archive.** Issues are off in this public
  repo; every issue (app reports, review findings, ideas) is filed in
  `plangdon84/word-mastermind-archive`, since a report can hold game data.
  Here, cite one in full (`plangdon84/word-mastermind-archive#166`), or as
  `Issue 166` with no `#` where that's too long: a bare `#166` is this
  repo's own #166. Issue numbers written before 8 October 2026 (in this
  file, the README and the plan's Done items) are the archive's. Never
  copy an issue's body here: describe the behaviour in your own words,
  with no secret word, Daily Rush answer, player name, report link, ID,
  code or key from it (`/triage-issues` plans them).
- **Close the issues a PR fixes.** Put
  `Closes plangdon84/word-mastermind-archive#N` on its own line under
  **Scope** for each archive issue the PR fully fixes, one keyword per
  issue (one `Closes` line each, never one listing two). An issue only
  partly fixed gets `Part of plangdon84/word-mastermind-archive#N` and
  stays open; a PR that only plans or mentions issues (triage, the dev
  plan) closes none. GitHub may not close an issue across repos on merge,
  so after merging, close each issue the PR fixed by hand as completed,
  with a comment naming the PR (`plangdon84/word-mastermind#N`);
  `/triage-issues` also closes any it finds still open.
- **Settle how it behaves before building it.** Questions about how the
  game behaves for players (rules, scoring, what a tap does, what others
  can see, who can do what) go in the PR's **Decisions needed before
  review** and are answered before the review starts, not found by it.
- **Watch every PR you open** (`subscribe_pr_activity`) and fix CI failures
  and review findings until it's green.
- **Keep PR status updates to one line.** When a PR event while watching
  is routine success (a deploy, a check started, a check passed), reply
  with one line and nothing else, e.g. "PR #63 live on preview.",
  "All checks passed.", "Server check started.", "Server check passed."
  Say more only when an event is unexpected (a failure, a conflict, a
  review finding) or needs the owner. When waiting on the owner, don't
  repeat what they owe on each update; re-list open questions only when
  asked.
- **Design questions mid-item:** pick the recommended option, build it, and
  list it under **Choices made** in the PR description for the owner to
  accept or change. Stop and ask only about game rules, scoring, anything
  that costs money, or security.
- **The PR description is the review.** The owner reviews from a phone
  and doesn't read code, so fill in every section of
  `.github/pull_request_template.md` in plain words: what changed, a
  tap-by-tap checklist for the preview link, choices made, the risk and
  the review findings.
- **Review gate:** a PR touching `worker/`, `worker/migrations/`, sign-in
  (`accounts`, `authRoutes`, `google`, `mail`), sync or secrets gets a
  `/code-review` and a `/security-review` pass before it's marked ready.
  Run both from a fresh session (`create_session`), not the one that wrote
  the code, and have it post one plain-English summary comment on the PR:
  each finding, its severity, and fixed or why not. Never leave a
  high-severity finding open on a PR marked ready. UI and docs PRs skip
  the gate. Aim for two rounds, never a trickle:
  - **Round 1 is the whole review.** `/code-review` at high effort and
    `/security-review` over the whole PR, reporting every finding at every
    severity in one list. Each suggested fix says what it could break.
    A finding that changes how the game behaves for players is marked
    **owner decision**, not fixed by the PR's session.
  - **Between rounds:** fix the accepted findings, push them together, and
    push nothing else until round 2 is done. A low finding is accepted as
    is or filed as an issue (in the archive); fix it in the PR only when the fix is a line
    or two and adds no new behaviour.
  - **Round 2 checks the fixes.** It reviews only the commits since round 1,
    given round 1's findings and outcomes (the **Reviews** table) so it
    doesn't raise them again. It reports only high or medium findings the
    fixes caused; anything else becomes an issue. A third round happens
    only for a high finding in round 2.
  - Before reviewing, the review session runs
    `git remote set-head origin main` (or `git fetch origin main` first),
    since `/security-review` needs `origin/HEAD`.
- **Chain the review back:** for a PR under the review gate, give the
  review session the PR's session ID. As its last step, after posting the
  summary comment, it schedules a one-shot Routine into the PR's session
  (`create_trigger` with `persistent_session_id` and `run_once_at` a minute
  out), which wakes it within a few minutes; if scheduling fails, it says
  so in a second PR comment. (`fire_trigger` on a Routine bound to the PR's
  session didn't wake it when tested; a scheduled one-shot did.) The PR's
  session reads the findings from the PR comment, not from the wake-up
  text, and keeps one fallback check-in (`send_later`, about 2 hours) until
  woken, then cancels it. If the check-in fires first, check the review
  session: start a new review if it failed, else set another check-in.
  After fixing round 1's findings, start round 2 in a fresh session the
  same way; the PR is ready once round 2's findings are fixed or accepted
  (a third round only for a high one).
- **Feedback goes in its own PR:** feedback on screens that arrives during
  an item goes on a separate branch and PR, never into the item's PR.
- **Keep the README true:** when a PR settles an Open Question, record the
  decision where it belongs and remove the question in the same PR.
- **Never paste or commit a secret.** Secrets go in the Cloudflare
  dashboard or `worker/.dev.vars`; ask the owner to set them.
